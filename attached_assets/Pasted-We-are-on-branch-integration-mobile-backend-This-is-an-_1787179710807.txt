# PROBLEM 1 — Receipt-level charges are not reliably preserved end-to-end

Real Pakistani receipts may contain:

* item subtotal
* GST / tax
* service charges
* delivery charges
* other additional charges
* discounts
* final payable total

Example real receipt:

Items/Subtotal: 7650
Service Charge: 765
Final Total: 8415

The system must understand:

`7650 + 765 = 8415`

and must NOT expect:

`7650 = 8415`

Inspect the complete path:

Receipt AI extraction
→ parser response schema
→ UFR
→ ReviewResponse
→ mobile UFR adapter
→ ReviewScreen
→ SaveRecordPayload
→ POST `/api/v1/financial-records`
→ deterministic validation
→ persistence metadata / database

Preserve these fields end-to-end wherever available:

* `subtotal`
* `tax`
* `gst`
* `service_charge`
* `delivery_charge` or other existing additional-charge field if already supported
* `discount`
* `total_amount`

Do not create duplicate concepts if the current schema already has equivalent fields.

Important rules:

* `total_amount` = FINAL payable total.
* `subtotal` = amount before taxes/additional charges/discounts.
* GST/tax must remain separate from item amounts.
* service charge must remain separate from item amounts.
* discounts must remain separate.
* AI extracts financial values.
* deterministic backend code performs reconciliation.
* Do not ask AI to calculate missing financial values.
* If AI cannot reliably read a field, preserve it as null rather than hallucinating.

For arithmetic reconciliation, use the existing supported fields to calculate:

`expected_total = subtotal/items_total + tax/GST + service_charge + other supported charges - discount`

Use zero only for OPTIONAL fields that are absent.

Use a small currency tolerance only for genuine rounding differences.

If dedicated database columns do not exist for optional receipt charges, preserve them inside the existing metadata structure for the demo rather than performing a risky database migration.

# PROBLEM 2 — Item-total mismatch must NOT permanently block saving

Current undesirable behavior:

items do not reconcile with total
→ backend returns HTTP 422
→ user cannot save

This is too strict for real-world receipts.

Legitimate causes include:

* GST
* service charges
* delivery fees
* discounts
* rounding
* tips
* packaging fees
* partial item extraction
* AI misreading one line item while final total is clearly readable

KharchAI must keep deterministic validation, but arithmetic mismatch should normally be a REVIEW WARNING rather than a permanent blocker.

Desired UX:

User presses Save
→ backend detects non-critical arithmetic mismatch
→ mobile shows confirmation dialog

Title:

`Amounts don't fully match`

Message:

`The item amounts do not fully reconcile with the final total. This may be caused by GST, service charges, discounts, rounding, or an extraction issue.`

Buttons:

`Review Amounts`

* dismiss dialog
* remain on Review Screen
* allow user to edit values

`Save Anyway`

* user explicitly confirms
* persist the record
* mark it as requiring review / preserve warning metadata
